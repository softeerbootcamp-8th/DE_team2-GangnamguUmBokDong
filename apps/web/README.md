# 대시보드 프론트엔드

대여소 재배치 관제 대시보드 화면이다. `apps/api`가 내려주는 데이터를 지도·리스트·그래프·상세 패널로 보여준다.

## 기술 스택

- **React + TypeScript**: 화면을 지도/리스트/그래프/상세 패널 컴포넌트 단위로 나눠서 관리한다.
- **Vite**: 개발 서버·번들러. 별도 웹팩 설정 없이 바로 개발할 수 있다.
- **Leaflet + react-leaflet**: 지도 렌더링과 마커 표시. 오픈소스라 별도 API 키 없이 쓸 수 있다.
- **순수 SVG**: 예측 그래프는 차트 라이브러리 없이 SVG로 직접 그린다(호버 크로스헤어, 범례, 직접 라벨 포함). 라이브러리 하나 안 붙여도 될 만큼 단순한 라인 차트라 이렇게 했다.

## 실행 방법

```bash
cd apps/web
npm install
npm run dev            # http://localhost:5173
```

백엔드 주소를 8000이 아닌 다른 포트로 띄웠다면 `.env.local`에 `VITE_API_BASE=http://localhost:<포트>`를 넣는다. `.env.local`은 커밋하지 않는다(`.gitignore` 처리됨).

## 폴더·파일 구조

```
web/
  index.html                 # Vite 엔트리 HTML, 페이지 타이틀
  package.json                # 의존성 목록 + npm scripts(dev/build/preview)
  package-lock.json
  vite.config.ts              # Vite 설정(React 플러그인 등록)
  tsconfig.json                # TypeScript 컴파일러 설정
  .env.local                  # (커밋 안 됨) VITE_API_BASE로 백엔드 주소 지정
  src/
    main.tsx                  # React 엔트리포인트, App을 DOM에 마운트
    App.tsx                   # 최상위 레이아웃 조립, 폴링·선택 상태 관리
    api.ts                    # 백엔드 fetch 헬퍼 + 응답 타입 정의
    format.ts                 # 시각 포맷 유틸(현재 시각, ISO 문자열 → 시:분)
    styles.css                # 전역 스타일, 색상 팔레트 변수, 레이아웃 그리드
    vite-env.d.ts              # Vite 클라이언트 타입 참조(import.meta.env 등)
    components/
      Header.tsx               # 상단 헤더: 제목 + 현재 시각 + 예측 기준 시각
      StationMap.tsx           # 지도 + 대여소 마커(Leaflet)
      AlertList.tsx            # 우측 작업 우선순위 리스트
      ForecastPanel.tsx        # 하단 왼쪽 패널: 선택된 대여소의 대여·반납 예측
      ForecastChart.tsx        # 실제 SVG 그래프(대여·반납 예측 라인)
      StockPanel.tsx           # 하단 가운데 패널: 선택된 대여소의 예측 재고
      StockChart.tsx           # 실제 SVG 그래프(예측 재고 라인 + 정원 기준선)
      DetailPanel.tsx          # 하단 오른쪽 패널: 선택된 대여소 상세 정보
```

## 화면 구성

- **대여소 지도** (`components/StationMap.tsx`): 마커 하나에 서로 다른 두 정보를 서로 다른 채널로 겹쳐서 보여준다. 색과 색을 같이 쓰면 두 색을 조합해서 읽어야 해서 한눈에 안 들어오고, 특히 "지금 텅 비었지만 곧 반납이 몰려 안 급한" 자가치유 케이스가 옅은 색으로 뭉개져 안 보이게 되므로, 색과 크기로 채널을 분리했다.
  - **채우기 색 = 방향, 짙기 = 긴급도**: `/alerts`의 `action_type`으로 방향을 정한다 — **supply_needed면 빨강 계열**, **retrieval_needed면 파랑 계열**, **normal이면 회색**(`markerColor()`). 그 위에서 `urgency_score`(0~100)만큼 회색과 방향색을 연속적으로 섞어서, 점수가 낮으면 회색에 가깝고 점수가 오를수록 짙어지다가 100점이면 순수한 빨강/파랑이 된다. 실시간 재고 비율로 방향을 따로 계산하지 않는 이유는, 아직 재고는 정상 범위인데 추세·예측으로만 위험이 잡힌 대여소(예: 신논현역, 2시간 뒤 위험)가 그 경우 색은 회색으로 나오면서 크기만 커져서 "큰데 방향을 알 수 없는" 마커가 되기 때문이다. urgency_score를 만든 바로 그 action_type을 색의 기준으로 쓰면 색·크기가 항상 같은 판단 결과를 가리킨다.
  - **마커 크기 = 긴급도 × 줌 배율**: `urgency_score`에 비례해서 기준 반지름을 9~20px 사이로 정하고(`markerRadius()`), 거기에 현재 줌 레벨에 따른 배율을 곱한다(`zoomScale()`, 기준 줌보다 4레벨 올라갈 때마다 2배). 지도를 확대하면 도로·건물이 커지는데 마커만 화면 픽셀 크기로 고정돼 있으면 상대적으로 쪼그라들어 보이므로, 마커도 같이 커지고 작아지게 했다. 줌 애니메이션이 진행되는 동안(`zoomend`가 아니라 `zoom` 이벤트를 듣는다) 크기도 실시간으로 따라가서 애니메이션 도중에 뚝뚝 끊기지 않는다. 재고 수 라벨도 그 마커의 실제 반지름만큼 띄우는 거리를 매번 다시 계산해서(`countIcon()`), 마커가 커져도 라벨이 안에 파묻히지 않는다.
  - **클릭 영역은 마커보다 넓게**: 시각적 마커 밑에 반지름이 `CLICK_PADDING`(10px)만큼 더 큰 투명한 원을 하나 더 깔아서, 마커 가장자리를 살짝 벗어나 눌러도 선택되게 했다. 마커 위에서는 원래 마커가 위에 있어서 호버 시 툴팁이 그대로 뜬다.
  - **재고 수 라벨**: 줌 레벨이 14 이상일 때만 마커 위에 현재 재고 수를 라벨로 띄운다(`COUNT_LABEL_MIN_ZOOM`). 대여소가 많아지면 항상 켜두기엔 지도가 지저분해져서, 확대했을 때만 정확한 값을 보여주는 방식으로 뒀다. 마커 색·크기는 우선순위(미래에 예상되는 방향·긴급도)라서, "지금 이 순간 실제로 몇 대인지"는 이 라벨로만 확인할 수 있다. 실제 재고 비율이 **20% 이하(부족)거나 80% 이상(과잉)이면 라벨 배경도 같은 색으로 칠해서**(`currentStatusColor()`) 지금 진짜 심하게 비었거나 찬 경우만 눈에 띄게 하고, 평범한 범위는 그냥 흰 배경 숫자로 둔다.
  - 선택 상태는 테두리(검정, `SELECTED_BORDER`)로 표시한다. 방향·긴급도 색과 헷갈리지 않도록 그 둘과 무관한 색을 썼다.
  - **선택 시 자동 이동**: 지도 마커든 우선순위 리스트 항목이든, 어느 쪽을 클릭해 대여소를 선택하든 지도가 그 대여소를 중심으로 이동하고 재고 수 라벨이 보이는 줌 레벨(`COUNT_LABEL_MIN_ZOOM`) 이상으로 확대된다. 이미 그보다 확대돼 있으면 더 축소하지 않고 그 줌을 유지한 채 이동만 한다. `flyTo()`가 아니라 `setView()`로 애니메이션 없이 한 번에 옮기는데, 애니메이션을 넣으면 지도 타일과 마커(SVG 벡터 레이어)가 프레임마다 따로 갱신돼 마커가 잠깐 멈춰 있다가 도착 시점에 튀어 보이는 문제가 있었기 때문이다.
- **작업 우선순위 리스트** (`components/AlertList.tsx`): `/alerts`를 `urgency_score` 내림차순으로 표시하고, 상단에 **전체/공급 필요/회수 필요** 탭으로 방향별로도 걸러볼 수 있다. 아이콘+라벨은 `statusOf()`(`format.ts`)로 정한다: **50점 이상 긴급, 20점 이상 심각, action_type이 정상이 아니면(점수가 0이어도) 주의, action_type도 정상이면 정상**. action_type이 정상이 아니면 `minutes_until_critical`을 "N시간 후 위험"으로 같이 보여준다(`formatUntilCritical()`, `format.ts`). urgency_score 자체가 어떻게 계산되는지는 [`../api/README.md`](../api/README.md)의 우선순위 점수 계산 참고.

지도와 리스트를 나누지 않고 하나의 통합 리스트(탭으로 필터만)로 둔 이유는, 재배치 트럭이 보통 회수 필요 대여소에서 걷은 자전거를 공급 필요 대여소에 채우는 식으로 한 동선에 묶어서 돌기 때문이다. 리스트 자체를 방향별로 완전히 쪼개면 그 동선 판단이 오히려 더 어려워져서, 동선 판단은 지도(위치 + 방향 + 긴급도가 한 마커에 다 있음)에서 하고 리스트의 탭은 "이 방향만 순서대로 보고 싶을 때" 쓰는 필터로만 뒀다.
- **반납/대여 수요 예측 그래프** (`components/ForecastPanel.tsx`, `ForecastChart.tsx`, 하단 왼쪽): 선택된 대여소의 `/stations/{sta_id}/forecast` 12시간 그래프(대여·반납 두 선). `action_type`이 처음 `normal`이 아니게 되는 시점을 그래프 위에 세로선 + 시각 라벨로 표시한다(공급 필요는 빨강, 회수 필요는 파랑). 12시간 안에 위험해지지 않는 대여소는 마커를 안 그린다.
- **예측 재고 그래프** (`components/StockPanel.tsx`, `StockChart.tsx`, 하단 가운데): 지금 재고에서 시작해 `predicted_bikes`를 이어 그린 선 하나 + 정원 위치의 점선 기준선. 대여·반납량(시간당 건수)과 재고(누적된 대수)는 단위가 달라서 한 그래프에 같이 넣으면 축이 두 개가 돼야 하므로, 처음부터 그래프 자체를 분리했다. "몇 시에 위험해지는지" 세로선 마커는 왼쪽 그래프에만 있고 여기엔 없다 — 재고 선이 0이나 정원에 닿는 지점 자체가 이미 위험 시점을 직관적으로 보여주기 때문이다. 대여소가 비콘 기반이라 반납이 막히지 않아 실제로 정원을 넘을 수 있어서, 재고 선이 점선 기준선 위로 올라갈 수 있다. y축은 정원과 실제 최댓값 중 큰 쪽에 맞춰 자동으로 늘어나서(`maxObserved`) 그 초과분이 잘리지 않는다.
- **대여소 상세 데이터** (`components/DetailPanel.tsx`, 하단 오른쪽): 선택된 대여소의 `/stations/{sta_id}` 상세 정보 + 수요 영향 사유(`forecast.reasons`) 목록.

지도 마커 클릭과 리스트 항목 클릭은 같은 선택 상태(`App.tsx`의 `selectedStationId`)를 공유해서 서로 연동된다. 예측(`/stations/{sta_id}/forecast`)은 `App.tsx`가 한 번만 가져와서 두 그래프 패널과 상세 패널이 같이 쓴다.

다섯 패널은 전부 하나의 CSS 그리드(`.dashboard-grid`, 3열 × 2행)에 들어가서 지도:우선순위 리스트가 2:1, 반납/대여 그래프:예측 재고 그래프:상세 데이터가 1:1:1 비율로 열을 나눠 쓴다. 위·아래 행을 각각 별도 flex 컨테이너로 뒀을 때는 위 행엔 패널 사이 여백(gap)이 1개, 아래 행엔 2개라 같은 비율을 줘도 세로 경계선이 몇 px씩 어긋났다. 하나의 그리드로 합쳐 열 트랙을 공유하게 하니, 지도 오른쪽 끝과 예측 재고 그래프 오른쪽 끝, 우선순위 리스트 왼쪽 끝과 상세 데이터 왼쪽 끝이 정확히 같은 세로줄에 맞는다.

## 폴링 주기

실시간 갱신은 웹소켓이 아니라 폴링으로 구현한다. 지통실 담당자 몇 명만 쓰는 내부 도구라 동시 접속자가 적고, 이런 규모에서는 지연을 줄이는 것보다 구현·운영을 단순하게 유지하는 게 더 이득이라고 판단했다.

| 대상 | 코드 위치 | 주기 |
|---|---|---|
| `/stations`, `/alerts` | `App.tsx`의 `POLL_INTERVAL_MS` | 15초 |
| `/status`(예측 기준 시각) | `Header.tsx`의 `STATUS_POLL_INTERVAL_MS` | 30초 |
| `/stations/{sta_id}/forecast` | `ForecastPanel.tsx` | 60초 |

백엔드 데이터 자체의 갱신 주기(재고·예측 둘 다 5분, [`../api/README.md`](../api/README.md) 참고)보다 훨씬 잦게 폴링한다. 대부분의 요청은 이전과 같은 값을 그대로 받게 되지만, 사용자가 적어서 그 정도 중복 요청은 비용상 무시할 만하고, 그 대신 값이 바뀐 직후 최대 몇 초~수십 초 안에 화면에 반영된다(5분 주기 그대로 폴링했다면 최악의 경우 갱신 후 거의 5분 가까이 화면이 안 바뀔 수 있다). 트래픽이 늘어나서 이 중복 요청이 부담되면, 그때 폴링 주기를 늘리거나 서버 측 캐싱을 넣는 걸 검토한다.

## 알려진 제약

- 아직 백엔드가 목데이터라서, 대여소 10곳 고정값 안에서만 동작한다. RDS 연동 후에는 [`../api/README.md`](../api/README.md)의 목데이터에서 실제 데이터로 섹션을 따라가면 된다.
- 지도 타일은 OpenStreetMap 기본 타일을 쓴다. 국내 공공 타일 소스로 교체할 수 있다(타일 소스 확정은 남은 조사 TODO).
- 마우스 휠 스크롤 한 번에 줌이 두 단계씩 뛴다면 앱 코드 문제는 아닐 가능성이 높다 — 줌 버튼(`+`/`-`) 클릭은 정확히 한 레벨씩만 바뀌는 걸 확인했고, 이 프로젝트는 별도 휠 이벤트 처리를 하지 않는다. 트랙패드·마우스 드라이버가 휠 이벤트를 두 번 쏘는 환경 이슈로 보이며, `MapContainer`에 `wheelDebounceTime={100}`(기본 40ms)을 줘서 짧은 간격으로 들어오는 휠 이벤트를 한 번으로 묶어보는 완화책만 넣어뒀다. 그래도 재현되면 실제 마우스/트랙패드 쪽을 의심해야 한다.
