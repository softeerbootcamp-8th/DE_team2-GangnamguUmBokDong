## 2. 문제 정의 수정하기

### 대상

서울시 시설관리공단 교통사업본부 공공자전거운영처 강남/강북공공자전거관리소 분배업무 운영·관리 담당자

### 문제

원래 방식 : 미리 고정된 목록 상의 품절/과잉 취약 대여소와 현재 품절/과잉이 일어난 대여소들만 재배치 작업 대상으로 고려한다.

- 실시간으로 변화하는 품절/과잉 위험이 있는 대여소들과 위험 정도를 알 수 없다.

### 해결방법

반납/대여 수요예측을 통해 품절/과잉 취약 대여소와 긴급한 정도를 실시간으로 파악해 재배치 대상 대여소 선정 의사결정을 돕는다.

- 대여소 근처 날씨, 주변인구, 대여이력 등의 데이터를 바탕으로 대여/반납 수요를 예측하여, 품절/과잉 위험이 있는 대여소들을 긴급도별로 나눠서 보여준다.

### INDEX
피크 시간대 전체 대여소 품절 시간
피크 시간대 :

- 평일 - 아침 7시~10시, 저녁 5시~8시

- 주말 - 오후 2시~6시

#### before -> after

총 100분 -> 총 70분

### 상세

데이터 수집 후 적재

미래 대여/반납 수요 예측

취약 정도를 판단하여 작업 우선순위 산출

한달마다 모델 정확도 테스트 후 일정 기준 미달시 그동안 새로 적재된 데이터를 추가하여 재학습

### 필요 자원

EC2 4대 (에어플로우, 데이터 수집/정제, 추론, 백엔드 API)

EMR serverless (피처 데이터 제작/학습용 스파크 작업)

RDS (실시간 서비스용 데이터 적재)

S3 (브론즈/학습용 데이터 적재)

## 6. api 호출과 저장 방식

5분 작업을 시작하면 

- 변경 전 : api 호출건 별로 브론즈 데이터 저장 → 정제 → 실버 데이터 저장이 이루어졌다.

    - 즉 2만건의 api 데이터에 대해서 1000건 페이지 별로 브론즈, 정제, 실버를 진행하고 다음 페이지를 진행하여 20번 반복했다.

이 방식의 경우 첫 페이지와 마지막 페이지 간에 시간차이가 있어서 동일 작업 간에 일관성이 깨질 수 있다.

- 변경 후 : 하나의 작업에 대해서 브론즈 데이터는 호출건 별로 저장하고 정제부터는 모아서 한번에 진행한다.

    - 즉 2만건의 api 데이터에 대해서 1000건 페이지 별로 브론즈는 즉시 20번 저장하고 이를 메모리에 모아두었다가 모든 호출이 끝나면 모아둔 데이터를 한번에 정제, 실버 데이터 저장을 진행한다.

이 방식의 경우 모든 예상 페이지의 수집이 완료된 후에만 Silver를 생성하여 동일 run 단위의 완전성과 처리 일관성을 보장하면서 작업 단위로 합치는 작업도 S3에서 하지 않아도 되며 브론즈 데이터는 바로바로 저장할 수 있다. 단 메모리에 모인 데이터가 일정량 이상 커지면 정제를 시작하여 메모리가 터지지 않게 한다.
