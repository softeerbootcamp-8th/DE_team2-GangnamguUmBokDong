# 재배치 시스템 point-in-time 백테스트

> **문서 상태:** 백테스트 구현은 `loader/evaluation/`에 있으며 계약·시뮬레이터
> 테스트로 검증한다. 아래 결과의 원천 CSV, 모델 bundle, MinIO station master와
> 생성 결과는 Git에 포함하지 않으므로, 동일한 고정 입력을 준비해야 수치를 재현할 수 있다.

이 평가는 과거 실측 재고에서 출발해 당시까지 관측 가능한 입력으로 실제 대여·반납
모델을 5분마다 다시 실행하고, 시민 대여 요청과 트럭 작업을 사건 순서대로 재생한다.
미래 실제 수요로 작업량을 만드는 이전 oracle 실험은 경로 디버깅 용도로만 남기며
시스템 성능 근거로 사용하지 않는다.

## 평가 질문

동일한 시작 재고와 실제 관측 수요에서 다음 세 상태를 비교한다.

1. `재배치 없음`: 시민 대여·반납만 재생한다.
2. `추정 기존 운영`: 시간별 실측 재고에서 시민 흐름을 제거한 운영 잔차를 적용한다.
3. `기존 정책`: 고정 모델 → urgency-v1 → route-v2를 5분마다 실행한다.
4. `개선 정책`: 같은 모델·점수에서 안전 수량·공급원 보호·route-v3를 적용한다.

재배치가 없는 별도의 사실 데이터가 존재하는 것은 아니다. `재배치 없음`과
`우리 시스템`은 같은 관측 수요를 사용하는 반사실 replay다. 대여가 실패하면 그
이용의 실제 반납도 제거한다.

기존 운영자의 station별 순개입은 각 정시 구간에서 다음 항등식으로 역산한다.

```text
운영 잔차 = 다음 실측 재고 - (현재 실측 재고 - 시민 대여 + 시민 반납)
```

공개 데이터로는 개입의 정확한 시각·경로·트럭을 알 수 없다. 따라서 잔차를 각 시간
구간의 초·중·말에 적용한 세 결과를 모두 기록한다. 세 경우 모두 구간 말 실측 재고를
오차 0으로 복원해야 한다.

## 사전 고정 계약

- 운영 판단 주기: 5분
- 기본 작업 블록: 120분
- 민감도: 60분·120분·180분을 모두 계산
- 트럭: 권역당 3대, 용량 20대
- 주행: 20km/h, 대여소 작업 3분
- 승인 지연: 자동 정책 평가를 위해 0분
- 배차 cutoff: 작업 블록 종료 전에 마지막 작업과 센터 복귀가 가능한 경로만 시작
- 작업당 최대 대여소: production 5곳, 기존 정책 민감도 비교 8곳
- 공통 이동 예산: 같은 구간의 기존 운영 잔차 중 `min(유입, 유출)`을 각 모델
  정책의 계획 이동 대수 상한으로 적용

120분은 모델의 예측 범위가 아니다. 현장 작업 단위를 검토하기 위해 사전에 정한
운영 블록이다. 특정 결과가 좋아 보이는 길이를 사후 선택하지 않도록 60·120·180분을
한 묶음으로 실행한다.

각 tick에서 진행 중 경로의 전체 계획량은 coverage로 차감된다. 작업이 끝난 트럭도
센터에 돌아오기 전까지 새 경로를 받을 수 없다. 이전 tick의 미승인 proposed 경로는
운영 publication과 같이 새 계산으로 교체된다.

개선 정책은 예측 이후 의사결정을 다음 순서로 고정한다.

1. 기존 urgency 점수와 `supply_needed`/`retrieval_needed` 판정은 유지한다.
2. 향후 2시간 평균 재고 경로에서 정원의 20%를 안전재고로 남기는 범위만 회수한다.
3. 한 판단에서 회수량은 현재 재고의 15%를 넘지 않는다.
4. 같은 공급원을 여러 동시 경로에 나누지 않고, 배차 후 60분 동안 다시 회수하지 않는다.
5. 현장 도착 시 재고가 달라졌으면 안전재고와 15% 상한을 다시 적용해 실제 회수량을
   줄인다.
6. 트럭 용량은 20대, 작업은 회수와 배치가 완결된 최대 5개 대여소 경로로 만든다.

모든 정책 값과 cooldown 대여소 집합은 publication fingerprint의 immutable 입력으로
남긴다. 따라서 같은 논리시각의 결과를 정책 설정과 DB 상태에서 재현할 수 있다.

## 정보시점과 누출 방지

- 시작 재고: 평가 시작 정시의 실측값만 사용하며 이후에는 정책별 시뮬레이션 상태만
  사용한다.
- 대여소 식별자: 재고 CSV의 공공 번호와 모델·station master의 내부 `ST-<suffix>`는
  같은 번호 공간이 아니다. 월 대여 이력의 두 ID 컬럼으로 1:1 crosswalk를 만들고,
  재고와 시민 사건을 내부 ID로 변환한 뒤 결합한다. 다대일·일대다 대응은 fail-closed한다.
- 대여 lag: `[T-100분, T-40분)`에 시작하고 T까지 반납되어 보이는 성공 이용만 센다.
- 반납 lag: `[T-60분, T)`의 성공 반납만 센다.
- 날씨: 게시시각 원장이 없어 기본값은 T보다 60분 이전인 최신 관측이다. 선택한
  관측시각과 cutoff를 모든 tick에 기록한다.
- 생활인구: 당일 실측은 4~5일 뒤 공개되므로 사용하지 않는다. 운영 nowcaster와
  같은 1~4주 전 자료의 0.4/0.3/0.2/0.1 가중평균을 사용하고, 모두 결측인 셀만
  5~8주 전 최근값으로 보완한다. 미래 또는 대상일 실측으로는 보완하지 않는다.
  실제 5분 tick의 12시간 추론이 조회할 날짜·시간만 요구하고, 그 셀마저 과거 8주
  모두 결측인 격자는 평가에서 제외해 개수와 ID를 provenance에 남긴다.
- 모델: `aws-temporary-model-2025-d20-h12-r20`의 원본 artifact bytes를 SHA-256으로
  고정한다. 매월 17일은 학습에서 제외된 test split이다.

결과 JSON에는 원천 CSV의 경로·크기·SHA-256, crosswalk 개수·SHA-256, 평가 station
master 내용 SHA-256, 생활인구 제외 표면, 모델 bundle SHA-256, 모든 tick의
정보시점 감사와 작업·stop 실제 수량이 포함된다.

## 실행

로컬 Compose가 실행 중이고 필요한 원천·모델·MinIO station master가 준비돼 있다면
`airflow-scheduler` 서비스의 loader 환경에서 실행한다. Compose 프로젝트명이 붙은
실제 컨테이너 이름을 직접 사용하지 않는다.

```bash
docker compose -f ops/compose/docker-compose.yml exec -T \
  -w /workspace/loader airflow-scheduler \
  env -u VIRTUAL_ENV UV_PROJECT_ENVIRONMENT=/opt/venvs/modules/loader \
  uv run --frozen python -m evaluation.run_policy_backtest \
  --date 2025-06-17 \
  --center hangnyeoul \
  --start-hour 6 \
  --evaluation-minutes 60 120 180 \
  --fleet-size 3 \
  --max-stops 5 8 \
  --rental-csv '../data/issue163-full-year/bootstrap/서울특별시 공공자전거 대여이력 정보_2506.csv' \
  --stock-csv '../data/issue163-full-year/bootstrap/대여소별 공공자전거 대여가능 수량_2506.csv' \
  --s3-endpoint http://minio:9000 \
  --s3-bucket issue163-full-year
```

기본 결과 경로는 `data/backtest-results/`이며 JSON은 전체 감사용, Markdown은 빠른
검토용이다. 이 경로는 컨테이너의 `/workspace/data/backtest-results/`와 같다. 원천과
결과는 Git에 포함하지 않는다.

초기 실험은 재고 CSV의 공공 번호와 station master의 내부 suffix를 같은 값으로
간주해 서로 다른 대여소의 재고·좌표·정원·모델 범주를 결합했다. 예를 들어 공공
781번은 내부 `ST-2007`인데 내부 `ST-781`과 합쳐졌다. 아래 결과는 월 이력의 1:1
crosswalk로 이 오류를 교정한 뒤 전부 다시 계산한 값이며, 교정 전 수치는 폐기한다.

## 개선 정책 선택과 독립 검증

6월과 10월 두 날짜만 교정 집합으로 사용해 실패 원인을 추적했다. 기존 정책은 큰
장기 잉여를 같은 공급원에서 여러 트럭으로 동시에 가져갔고, 단순 보호 시간이나
포아송 `z` 완충은 해당 반례의 회수량을 바꾸지 못했다. 다음 순서로 구조를 좁혔다.

- 동일 공급원 동시 분할 금지: 180분 미충족 변화 `+26 → +8`
- 회수 후 60분 cooldown: `+8 → +2`
- 회수량을 현재 재고의 15%로 제한: `+2 → -4`

15% 후보를 선택한 뒤 값은 동결했다. 선택에 사용하지 않은 3·4·5·7·8·9·11·12월
8개 날짜에서 60/120/180분을 검증했으며, 180분은 4개 날짜 개선·4개 동일·악화
0개였다. 마지막으로 cooldown의 기준을 실제 DB에서 재현 가능한 배차시각으로 통일한
뒤 전체 10개월을 다시 실행했다.

| 구간 | 정책 | 관측 요청 | 충족률 | 미충족 변화 | 품절 대여소-분 변화 | 날짜별 개선/동일/악화 | 이동 | 차량 분 |
|---:|---|---:|---:|---:|---:|---:|---:|---:|
| 60분 | 개선 정책 | 2,252 | 100.0000% | 0 | -1.31% | 0/10/0 | 49 | 598.0 |
| 120분 | 개선 정책 | 6,630 | 99.9849% | 0 | -5.55% | 0/10/0 | 184 | 2,021.3 |

180분 재배치 없음은 13,369건 중 59건을 충족하지 못했고, 개선 정책은 44건으로
15건 줄였다. 기존 max-5 정책은 77건으로 재배치 없음보다 18건 많았다. 개선 정책은
기존 max-5보다 이동량도 `485 → 363대`, 차량시간도 `3,775.6 → 3,774.4분`이다.
60/120분은 시민 대여 실패를 늘리지 않으면서 빈 대여소 시간을 줄였다.

이는 고정된 관측 성공 수요 replay의 결과이며 인과적 운영 개선율은 아니다. 다만
같은 입력·모델·자원에서 기존 정책의 공급원 손상을 제거하고, 선택에 쓰지 않은 날짜
에서도 악화 없이 재현됐다는 정책 채택 근거로 사용한다.

## 해석 가능한 주장과 불가능한 주장

이 평가로 직접 말할 수 있는 것은 다음뿐이다.

> 고정된 관측 수요와 명시한 모의 트럭 자원, 기존 운영에서 역산한 이동 대수 상한
> 아래에서 우리 정책이 재배치 없음 및 정책 변형과 어떻게 달라지는가.

아직 다음 주장은 할 수 없다.

> 우리 시스템이 실제 기존 운영보다 시민의 전체 잠재 수요를 일정 비율 더 충족한다.

이유는 네 가지다.

1. 기록에는 현실에서 자전거가 없어 시도하지 못한 잠재 수요가 없다.
2. 기존 운영자의 route·truck·정확한 작업시각 로그가 없다.
3. 고정 모델은 2025년 전체의 다른 날짜로 사후 학습돼, 2025-06-17 당시 실제로
   배포돼 있던 모델은 아니다.
4. 같은 이동 대수 상한은 강제했지만 기존 운영과 같은 차량 대수·차량시간인지는
   증명할 수 없다.

CLI는 이 조건을 `EvidenceGate`로 저장하며 현재
`causal_superiority_vs_legacy_allowed=false`,
`publication_grade_system_claim_allowed=false`로 고정한다. 발표 근거로 승격하려면
기존 작업 로그와 실패 수요 또는 현장 A/B 실험, 여러 날짜·권역 반복 검증이 필요하다.
