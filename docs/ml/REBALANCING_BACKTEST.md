# 재배치 시스템 point-in-time 백테스트

이 평가는 과거 실측 재고에서 출발해 당시까지 관측 가능한 입력으로 실제 대여·반납
모델을 5분마다 다시 실행하고, 시민 대여 요청과 트럭 작업을 사건 순서대로 재생한다.
미래 실제 수요로 작업량을 만드는 이전 oracle 실험은 경로 디버깅 용도로만 남기며
시스템 성능 근거로 사용하지 않는다.

## 평가 질문

동일한 시작 재고와 실제 관측 수요에서 다음 세 상태를 비교한다.

1. `재배치 없음`: 시민 대여·반납만 재생한다.
2. `추정 기존 운영`: 자전거 ID 연속 이력과 시간별 실측 재고 잔차가 허용하는
   운영 범위를 적용한다.
3. `우리 시스템`: 고정 모델 → 현행 urgency-v1 → 현행 route-v2를 5분마다 실행하고
   트럭의 이동·회수·배치·센터 복귀를 재생한다.

재배치가 없는 별도의 사실 데이터가 존재하는 것은 아니다. `재배치 없음`과
`우리 시스템`은 같은 관측 수요를 사용하는 반사실 replay다. 대여가 실패하면 그
이용의 실제 반납도 제거한다.

동일 자전거의 이전 반납지와 다음 대여지가 다르면, 그 자전거가 두 사건 사이에
이동했다는 사실은 관측된다. 이때 알 수 있는 것은 출발지·도착지와 가능 시간구간뿐이다.

```text
이동 가능시각 ∈ [이전 반납시각, 다음 대여시각]
```

이 구간이 길면 평가 시간 안에 이동했는지는 알 수 없다. 누락 이용, 정비·보관소 이동도
섞일 수 있으므로 ID 후보를 곧바로 재배치 작업이나 정확한 이동시각으로 간주하지 않는다.

별도로 기존 운영자의 station별 순개입은 각 정시 구간에서 다음 항등식으로 역산한다.

```text
운영 잔차 = 다음 실측 재고 - (현재 실측 재고 - 시민 대여 + 시민 반납)
```

ID 후보가 가능한 정시 구간에서 출발지의 음의 잔차와 도착지의 양의 잔차에 동시에
맞으면 `잔차 양립`으로 기록한다. 짧은 이동 가능구간부터 후보를 한 번씩만 쓰지만,
이는 가능한 재구성 하나일 뿐 실제 작업시각의 복원이 아니다. 결과 범위에는 다음
6개 시나리오를 모두 포함한다.

1. ID를 할당하지 않고 잔차를 정시 구간의 초·중·말에 적용한 세 경우
2. ID와 잔차가 양립하는 가능한 할당 뒤 남은 잔차를 초·중·말에 적용한 세 경우

여섯 경우 모두 구간 말 실측 재고를 오차 0으로 복원해야 한다. ID 후보 중 1·6·24시간
이내 개수와 전체 간격 중앙값을 별도 기록해 장기 후보가 만든 설명력을 숨기지 않는다.

## 사전 고정 계약

- 운영 판단 주기: 5분
- 기본 작업 블록: 120분
- 민감도: 60분·120분·180분을 모두 계산
- 트럭: 권역당 3대, 용량 20대
- 주행: 20km/h, 대여소 작업 3분
- 승인 지연: 자동 정책 평가를 위해 0분
- 배차 cutoff: 작업 블록 종료 전에 마지막 작업과 센터 복귀가 가능한 경로만 시작
- 경로 변형: 작업당 최대 대여소 5곳과 8곳
- 공통 이동 예산: 같은 구간의 기존 운영 순잔차 중 `min(유입, 유출)`을 각 모델
  정책의 계획 이동 대수 상한으로 적용한다. 이는 자전거 ID로 확정한 실제 이동량이
  아니라 비교를 위한 공통 잔차 상한이다.

120분은 모델의 예측 범위가 아니다. 현장 작업 단위를 검토하기 위해 사전에 정한
운영 블록이다. 특정 결과가 좋아 보이는 길이를 사후 선택하지 않도록 60·120·180분을
한 묶음으로 실행한다.

각 tick에서 진행 중 경로의 전체 계획량은 coverage로 차감된다. 작업이 끝난 트럭도
센터에 돌아오기 전까지 새 경로를 받을 수 없다. 이전 tick의 미승인 proposed 경로는
운영 publication과 같이 새 계산으로 교체된다.

## 정보시점과 누출 방지

- 시작 재고: 평가 시작 정시의 실측값만 사용하며 이후에는 정책별 시뮬레이션 상태만
  사용한다.
- 대여소 식별자: 재고 CSV의 공공 번호와 모델·station master의 내부 `ST-<suffix>`는
  같은 번호 공간이 아니다. 월 대여 이력의 두 ID 컬럼으로 1:1 crosswalk를 만들고,
  재고와 시민 사건을 내부 ID로 변환한 뒤 결합한다. 다대일·일대다 대응은 fail-closed한다.
- 자전거 연속성: 월 파일 전체를 자전거 ID별 대여시각 순서로 검사한다. 겹치는 이용쌍은
  후보에서 제외하고 수를 기록한다. 월 경계를 넘는 이전·다음 이용은 관측되지 않으므로
  ID 결과를 완전한 이동 로그로 주장하지 않는다.
- 대여 lag: `[T-100분, T-40분)`에 시작하고 T까지 반납되어 보이는 성공 이용만 센다.
- 반납 lag: `[T-60분, T)`의 성공 반납만 센다.
- 날씨: 게시시각 원장이 없어 기본값은 T보다 60분 이전인 최신 관측이다. 선택한
  관측시각과 cutoff를 모든 tick에 기록한다.
- 생활인구: 당일 실측은 4~5일 뒤 공개되므로 사용하지 않는다. 운영 nowcaster와
  같은 1~4주 전 자료의 0.4/0.3/0.2/0.1 가중평균을 사용하고, 모두 결측인 셀만
  5~8주 전 최근값으로 보완한다. 미래 또는 대상일 실측으로는 보완하지 않는다.
  실제 5분 tick의 12시간 추론이 조회할 날짜·시간만 요구하고, 그 셀마저 과거 8주
  모두 결측인 격자는 평가에서 제외해 개수와 ID를 provenance에 남긴다.
- 모델: `aws-temporary-model-2025-d20-h12-r20`의 원본 artifact bytes를 SHA-256으로
  고정한다. 매월 17일은 학습에서 제외된 test split이다.

결과 JSON에는 원천 CSV의 경로·크기·SHA-256, crosswalk 개수·SHA-256, 자전거 연속
이용쌍·위치 변경쌍·겹침쌍, ID 후보의 검열 상태와 잔차 양립성, 평가 station master
내용 SHA-256, 생활인구 제외 표면, 모델 bundle SHA-256, 모든 tick의 정보시점 감사와
작업·stop 실제 수량이 포함된다. 원본 자전거 ID는 결과에 남기지 않고 SHA-256으로
가명화한다.

## 실행

대시보드 Docker를 내리거나 다시 만들 필요가 없다. 현재 scheduler 컨테이너의 loader
환경을 사용하면 고정 MinIO volume의 학습 station master를 그대로 읽는다.

```bash
docker exec -w /workspace/loader \
  umbokdong-dashboard-live-airflow-scheduler-1 \
  /workspace/loader/.venv/bin/python -m evaluation.run_policy_backtest \
  --date 2025-06-17 \
  --center hangnyeoul \
  --start-hour 6 \
  --evaluation-minutes 60 120 180 \
  --fleet-size 3 \
  --max-stops 5 8 \
  --rental-csv '../data/issue163-full-year/bootstrap/서울특별시 공공자전거 대여이력 정보_2506.csv' \
  --stock-csv '../data/issue163-full-year/bootstrap/대여소별 공공자전거 대여가능 수량_2506.csv' \
  --s3-endpoint http://minio:9000 \
  --s3-bucket issue163-full-year
```

기본 결과 경로는 `data/backtest-results/`이며 JSON은 전체 감사용, Markdown은 빠른
검토용이다. 원천과 결과는 Git에 포함하지 않는다.

초기 실험은 재고 CSV의 공공 번호와 station master의 내부 suffix를 같은 값으로
간주해 서로 다른 대여소의 재고·좌표·정원·모델 범주를 결합했다. 예를 들어 공공
781번은 내부 `ST-2007`인데 내부 `ST-781`과 합쳐졌다. 아래 결과는 월 이력의 1:1
crosswalk로 이 오류를 교정한 뒤 전부 다시 계산한 값이며, 교정 전 수치는 폐기한다.

교정된 기준선에서 120분 정책은 10월 하루에만 크게 악화해 집계 미충족을 10~12건
늘렸다. 180분은 두 설정 모두 3일 악화했고, 최대 8곳은 서비스 손상이 더 컸다.
품절 대여소-분은 줄었지만 시민 대여 실패를 늘렸으므로 현행 정책은 그대로 운영
최적이라고 볼 수 없다. 작업 상한보다 수거 안전재고와 동시 분할 정책을 먼저
개선해야 한다.

자전거 ID 연속 이력과 재고 잔차의 양립성은 다음과 같다. `ID 후보`는 평가 창과
이동 가능구간이 겹치는 위치 변경쌍이고, `잔차 양립`은 같은 후보가 출발지 감소와
도착지 증가를 동시에 설명할 수 있는 가능한 할당 수다.

| 구간 | ID 후보 | 한 시간 내 확정 | 잔차 양립 | 6시간 이내 | 24시간 이내 | 잔차 설명 |
|---:|---:|---:|---:|---:|---:|---:|
| 60분 | 10,553 | 0 | 43 | 2 | 15 | 50.8% |
| 120분 | 10,872 | 0 | 234 | 8 | 114 | 57.6% |
| 180분 | 11,408 | 1 | 655 | 41 | 256 | 62.5% |

후보 수에 비해 짧은 가능구간이 매우 적다. 따라서 ID 연결은 이동의 출발지·도착지와
잔차 방향을 보강하지만, 기존 운영자의 정확한 작업시각·경로를 복원하지는 못한다.
잔차만 적용한 세 시각과 ID 양립 후보를 먼저 할당한 세 시각을 함께 범위로 유지한다.

추정 기존 운영의 10일 합산 균형 이동 예산은 60/120/180분에 각각 50/224/644대다.
시각 가정에 따른 품절 대여소-분 범위는 각각 15,547.4~15,716.1,
32,924.4~33,416.7, 51,682.7~52,723.9이다. 180분 일부 시각 가정은 음수 재고를
만들어 정확한 작업 시각이 없다는 한계를 드러낸다. 따라서 이 범위는 참고용이며
우리 정책과의 인과적 우열 계산에는 사용하지 않는다.

## 해석 가능한 주장과 불가능한 주장

이 평가로 직접 말할 수 있는 것은 다음뿐이다.

> 고정된 관측 수요와 명시한 모의 트럭 자원, 기존 운영에서 역산한 이동 대수 상한
> 아래에서 우리 정책이 재배치 없음 및 정책 변형과 어떻게 달라지는가.

아직 다음 주장은 할 수 없다.

> 우리 시스템이 실제 기존 운영보다 시민의 전체 잠재 수요를 일정 비율 더 충족한다.

이유는 네 가지다.

1. 기록에는 현실에서 자전거가 없어 시도하지 못한 잠재 수요가 없다.
2. 기존 운영자의 route·truck·정확한 작업시각 로그가 없다.
3. 고정 모델은 2025년 전체의 다른 날짜로 사후 학습돼, 2025-06-17 당시 실제로
   배포돼 있던 모델은 아니다.
4. 같은 이동 대수 상한은 강제했지만 기존 운영과 같은 차량 대수·차량시간인지는
   증명할 수 없다.

CLI는 이 조건을 `EvidenceGate`로 저장하며 현재
`causal_superiority_vs_legacy_allowed=false`,
`publication_grade_system_claim_allowed=false`로 고정한다. 발표 근거로 승격하려면
기존 작업 로그와 실패 수요 또는 현장 A/B 실험, 여러 날짜·권역 반복 검증이 필요하다.
