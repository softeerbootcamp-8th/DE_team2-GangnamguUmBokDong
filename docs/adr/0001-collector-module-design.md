# bronze 원본과 silver 정제본을 한 실행에서 만든다

## 배경
실시간 API는 수집 시점을 놓치면 그 시점 데이터를 다시 받을 수 없다. 반면 검증·정제 정책은 앞으로 계속 바뀔 수 있다.

## 결정
API 응답을 가공 없이 bronze에 먼저 저장하고, 메모리에 남아 있는 그대로 검증·정제해 silver까지 같은 실행에서 만든다.

## 결과
정책이 바뀌어도 재수집 없이 bronze만 다시 처리하면 된다. 대신 저장 용량은 bronze와 silver 두 벌이 든다.

---

# 검증 규칙을 소스별 YAML config로 선언한다

## 배경
소스가 7개이고 앞으로 더 늘어난다. 컬럼의 허용 타입·정상 범위·필수 여부가 소스마다 전부 다르다.

## 결정
컬럼별 스펙과 적용할 정책 함수 이름을 `collector/sources/{source}.yaml`에 적고, 로드 시점에 스키마와 정책 이름의 존재 여부를 검증한다.

## 결과
소스를 추가할 때 공통 코드를 고치지 않는다. config 오타는 수집이 시작되기 전에 잡힌다.

---

# 정책 함수는 이름으로 등록된 레지스트리에서 찾는다

## 배경
YAML에는 함수를 직접 쓸 수 없으므로 문자열과 실제 함수를 이어줄 방법이 필요하다.

## 결정
`@policy` · `@row_policy` 데코레이터로 공통 함수를 이름과 함께 등록하고, config의 문자열로 조회해 호출한다.

## 결과
새 정책이 필요하면 함수 하나만 추가하면 되고 검증 엔진 코드는 그대로 둔다.

---

# 정책 기본값을 필수·선택 × 결측·이상치 4분면으로 둔다

## 배경
컬럼마다 정책을 전부 적으면 컬럼이 수십 개인 소스에서 같은 설정이 계속 반복된다.

## 결정
소스마다 4분면 기본 정책을 선언하고, 예외가 필요한 컬럼만 `on_missing`·`on_outlier`로 덮어쓴다.

## 결과
대부분의 컬럼은 스펙만 적으면 되고, 특별한 처리가 필요한 컬럼만 눈에 띈다.

---

# 정책을 컬럼 단계와 행 단계로 나눠 적용한다

## 배경
기상청의 `-999` 같은 센티널 값은 컬럼 단위로 고쳐야 하지만, 위경도 중 하나만 결측인 경우처럼 행 전체를 봐야 판단되는 문제도 있다.

## 결정
컬럼 정책으로 값을 먼저 교정한 뒤, 행 정책이 이슈 목록 전체를 보고 행의 유지·폐기를 최종 판정한다.

## 결과
값 교정과 행 판정이 서로 간섭하지 않는다. 행 정책은 선택이므로 필요 없는 소스는 생략한다.

# 실패하면 완료된 단계를 건너뛰고 재개한다

## 배경
Airflow 재시도는 태스크를 처음부터 다시 돌리는데, 5분 주기 실시간 API는 그 사이 다른 시점의 데이터를 내려준다.

## 결정
`(source_id, window_start)`를 멱등 키로 삼아 manifest에 진행 단계를 기록하고, bronze가 이미 있으면 fetch를 건너뛰고 정제부터 재개한다.

## 결과
재시도해도 원래 시점의 데이터를 잃지 않고 API 호출도 아낀다. 이미 완료된 실행은 아무것도 하지 않고 끝난다.

# 실행 상태와 품질 집계를 S3 manifest에 남긴다

## 배경
어느 배치가 어디까지 진행됐는지, 몇 건이 버려졌는지 확인할 방법이 필요하다.

## 결정
상태(RUNNING·SUCCEEDED·PARTIAL·FAILED·EMPTY·SKIPPED)와 진행 단계, 건수 집계, 컬럼별 이슈 수, config 해시를 배치마다 S3 manifest 파일에 기록한다.

## 결과
collector가 DB 커넥션 없이 동작한다. 품질 추이 조회가 필요해지면 manifest를 Postgres로 적재하는 태스크를 나중에 붙인다.

# 배치의 성패는 drop 비율 임계치로 가른다

## 배경
필수 컬럼 결측이 1%인 상황과 60%인 상황은 전혀 다른데, 행 단위 정책만으로는 구분되지 않는다.

## 결정
config의 `max_drop_ratio`를 넘으면 배치를 FAILED로, 이내면 PARTIAL로 처리한다.

## 결과
API가 망가진 경우와 자잘한 결측을 구분해 대응할 수 있다.

# 교정된 행은 silver의 _row_status 컬럼으로 표시한다

## 배경
값이 교정된 행은 silver만 봐서는 원래 값인지 교정된 값인지 알 수 없다.

## 결정
silver에 `_row_status`(ok·repaired) 컬럼 하나만 추가하고 이슈 상세는 넣지 않는다.

## 결과
하류에서 무결한 행만 골라 쓸 수 있다. 상세가 필요하면 bronze와 config 해시로 재현한다.

# 폐기된 행은 사유와 함께 quarantine에 남긴다

## 배경
버려진 행을 확인할 수 없으면 검증 정책이 적절한지 판단할 수 없다.

## 결정
폐기된 행을 이슈 목록과 함께 `quarantine/`에 JSONL로 저장한다.

## 결과
행 단위 로그를 남기지 않고도 문제 행을 추적할 수 있다.

# 어댑터는 소스가 아니라 API 제공처 단위로 만든다

## 배경
소스는 7개지만 서울 열린데이터광장 5종은 인증과 페이지네이션 규약이 동일하다.

## 결정
서울 열린데이터광장과 기상청 API 허브 두 개의 어댑터만 만들고, 소스별 차이는 config의 `adapter_params`로 흡수한다.

## 결과
같은 제공처의 소스가 늘어나면 YAML 파일만 추가하면 된다.

---

# 어댑터가 응답을 행 = 레코드 형태로 정규화한다

## 배경
기상청 API는 기온·습도·풍속을 각각 별도 행으로 내려주는 long format이라 실제 값이 전부 `obsrValue` 한 컬럼에 들어간다. 컬럼마다 정상 범위를 선언하는 검증 방식과 맞지 않는다.

## 결정
어댑터 계약을 `fetch`(원본 획득)와 `normalize`(행 = 레코드로 변환) 두 단계로 나누고, 소스별 응답 구조 차이는 `normalize`가 흡수한다.

## 결과
검증 엔진과 config 스키마는 소스 구조와 무관하게 유지된다. bronze는 정규화 전 원본을 담으므로, 재개할 때는 bronze를 읽어 `normalize`부터 다시 수행한다.

# 행 검증은 dict 순회로 처리한다

## 배경
정책 함수가 컬럼마다 다르고 행 전체도 봐야 하므로 pandas 벡터화와는 맞지 않는다.

## 결정
행을 dict로 순회하며 정책 함수에 `(value, spec, row, ctx)`를 넘긴다.

## 결과
정책 함수가 단순해진다. 현재 데이터 규모에서는 성능도 충분하다.

# 검증 엔진은 collector 안에 둔다

## 배경
정제가 collector 실행 안에서 끝나므로 지금은 검증 로직을 함께 쓸 다른 프로젝트가 없다.

## 결정
`libs/core`가 아니라 `collector/validation/`에 두고, 다른 소비자가 생기면 그때 core로 옮긴다.

## 결과
팀 공용 라이브러리를 건드리지 않아 변경이 빠르다.
