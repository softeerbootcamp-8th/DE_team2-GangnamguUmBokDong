# 외부 데이터 장애가 전체 서비스로 전파되지 않는 구조

## 강조할 핵심

우리 시스템은 외부 API가 항상 정상적으로 응답한다고 가정하지 않았습니다. 
데이터의 중요도와 대체 가능성을 기준으로 실패 처리 방식을 구분하고, 일부 외부 데이터가 실패해도 정상적으로 제공할 수 있는 핵심 서비스는 계속 운영하도록 설계했습니다.

중요한 점은 모든 실패를 무조건 무시하거나 모든 작업을 계속 실행한 것이 아니라는 것입니다.

- 필수 데이터가 실패하면 잘못된 결과가 게시되지 않도록 신규 추론과 게시를 중단합니다.
- 이전 정상 데이터로 대체할 수 있으면 정해진 freshness 범위 안에서 fallback합니다.
- 독립적으로 처리할 수 있는 작업은 별도 의존성으로 구성해 장애 전파 범위를 제한합니다.

## 데이터 중요도에 따른 처리

### 필수 데이터

재고·대여이력·생활인구는 수요 추론에 필요한 필수 입력입니다. 이 데이터가 정상적으로 준비되지 않은 상태에서 계산을 계속하면 결과가 생성되더라도 신뢰성을 보장할 수 없습니다.

따라서 필수 데이터가 실패하면 신규 추론과 Gold 게시를 중단합니다. 서비스 데이터를 비우는 대신 이전 정상 Gold를 유지해 불완전한 신규 결과가 사용자에게 노출되지 않게 합니다.

### fallback 가능한 데이터

날씨는 신규 수집에 실패하더라도 이전에 검증된 정상 snapshot을 제한적으로 사용할 수 있습니다. 날씨 API 하나의 일시적인 장애 때문에 재고와 생활인구 등 정상적으로 준비된 데이터까지 버리고 예측 서비스 전체를 중단하는 것은 과도하다고 판단했습니다.

따라서 신규 날씨 수집이 실패하면 허용된 lookback 범위 안에서 마지막 `SUCCEEDED` snapshot을 찾습니다. 사용할 수 있는 snapshot이 있으면 `STALE`로 명시하고 추론을 계속하며, 범위 안에 정상 snapshot이 없으면 신규 추론을 중단합니다.

## 실제 발생 사례: 기상청 API 실패에도 추론 정상 진행

### 장애 발생

실제 운영 중 기상청 API의 응답 시간이 길어져 날씨 Collector가 제한 시간 안에 수집을 완료하지 못한 사례가 있었습니다. 장애 당시 timeout은 60초였고, 기상청 API 응답이 이를 초과하면서 날씨 수집 태스크가 `FAILED`로 종료됐습니다.

하지만 재고·대여이력·생활인구 등 필수 데이터는 정상적으로 준비되어 있었고, 수요 추론과 Gold 게시도 정상적으로 완료됐습니다. 장애 영향은 날씨 갱신 지연으로만 제한됐으며 예측 서비스 전체의 중단으로 확대되지 않았습니다.

![날씨 수집에 실패해도 문제없이 작동하는 대시보드](./weather_failed_dag_success.png)

### `retries=0`으로 worker 장기 점유 방지

날씨 Collector에는 `retries=0`을 적용했습니다. 같은 DAG Run에서 응답이 느린 외부 API를 반복 호출하면 Airflow worker가 계속 점유되고 후속 작업과 다음 5분 실행까지 지연될 수 있기 때문입니다.

정해진 timeout 안에 완료되지 않은 수집은 `FAILED`로 명확히 기록하고, 다음 5분 tick을 새로운 재시도 기회로 사용합니다. 실패 사실은 숨기지 않으면서 현재 실행이 외부 API를 장시간 붙잡는 상황을 방지합니다.

### `weather_ready_gate`로 실패 전파 차단

날씨 Collector 하위의 `weather_ready_gate`에는 `TriggerRule.ALL_DONE`을 적용했습니다. 상위 날씨 태스크가 `SUCCESS`, `FAILED`, `SKIPPED` 중 어떤 상태로 끝나더라도 gate는 실행됩니다.

실제 장애 당시 날씨 Collector는 `FAILED`로 남았지만 `weather_ready_gate`는 통과했습니다. 이를 통해 다음 두 판단을 분리했습니다.

- 이번 시각의 신규 날씨 수집에 성공했는가?
- 후속 추론에 사용할 수 있는 날씨 데이터가 존재하는가?

`ALL_DONE`은 실패를 성공으로 바꾸는 설정이 아닙니다. 실패 상태와 로그는 그대로 보존하면서, 후속 작업이 fallback 가능 여부를 직접 판단할 기회를 주는 설정입니다.

### freshness 범위 안의 마지막 정상 날씨 사용

`prepare_serving_plan`은 실패한 신규 날씨 결과를 사용하지 않고 기준 시각 이전의 마지막 `SUCCEEDED` snapshot을 탐색합니다.

- 단기예보: 기준 시각 이전 최대 24시간
- 초단기예보: 기준 시각 이전 최대 6시간

현재 요청 시각과 동일한 snapshot은 `CURRENT`, 이전 시각의 snapshot은 `STALE`로 기록합니다. 따라서 이전 날씨를 사용하더라도 이를 신규 날씨처럼 취급하거나 숨기지 않습니다.

이 사례에서는 lookback 범위 안에 이전 `SUCCEEDED` 날씨가 있었고, 재고와 생활인구 등 필수 데이터도 정상이었습니다. Serving plan은 해당 입력을 고정했고 수요 추론, Gold release, 긴급도 산정과 재배치 경로 생성까지 계속 진행했습니다.

![최신 수집한 날씨 데이터가 아님을 보여주는 대시보드](./weather_delay_dashboard.png)

### 수집 freshness와 추론 freshness의 구분

날씨 freshness는 두 단계에서 사용합니다.

첫 번째는 **신규 수집이 필요한지 판단하는 기준**입니다.

- 초단기실황과 초단기예보는 마지막 성공 수집 이후 10분이 지나면 다시 수집합니다.
- 단기예보는 기본적으로 마지막 성공 수집 이후 3시간을 기준으로 합니다.
- 다만 단기예보는 단순히 3시간 경과 여부만 확인하지 않고, 기상청의 새 발표 기준시각이 열렸는지도 함께 확인합니다.
- 단기예보 발표 시각은 02·05·08·11·14·17·20·23시이며, 실제 API 제공 시점을 고려해 각 기준시각의 10분 이후부터 새 발표본을 수집 대상으로 판단합니다.
- 마지막 수집 후 3시간이 지나지 않았더라도 이전 수집 이후 새로운 발표 기준시각이 열렸다면 다음 5분 tick에서 즉시 수집합니다.
- 아직 갱신 주기가 되지 않았다면 수집 태스크만 `SKIPPED`하고 기존 정상 snapshot으로 진행합니다.

예를 들어 13시 50분에 11시 발표본을 수집했다면 단순 3시간 주기만 적용할 경우 다음 수집이 16시 50분까지 늦어질 수 있습니다. 현재 정책은 14시 10분부터 14시 발표본이 열린 것을 감지하므로, 다음 5분 tick에서 신규 단기예보를 수집합니다. 이를 통해 불필요한 중복 호출은 피하면서 새로운 발표본의 반영이 3시간 가까이 지연되는 문제를 막습니다.

두 번째는 **과거 데이터를 추론에 사용할 수 있는지 판단하는 기준**입니다.

- 신규 수집이 실패하면 lookback 범위 안의 마지막 성공 snapshot을 찾습니다.
- 과거 snapshot을 선택하면 `STALE`로 기록합니다.
- 범위 안에 정상 snapshot이 없으면 신규 Serving plan과 추론을 중단합니다.

즉, freshness는 API 호출 횟수를 줄이는 기능인 동시에 fallback의 시간적 상한을 정하는 안전장치입니다.

### 장애 이후 자동 재시도와 timeout 유지

실패한 수집은 마지막 성공 시각을 갱신하지 않습니다. 따라서 다음 5분 tick에서 freshness gate가 다시 신규 수집 대상으로 판단하고 기상청 API 호출을 재시도합니다.

날씨 Collector의 timeout은 기존과 동일하게 60초를 유지합니다. 응답 지연이 발생하더라도 현재 DAG Run에서 외부 API를 장시간 점유하지 않고, 검증된 이전 날씨로 추론을 계속한 뒤 다음 5분 tick에서 다시 수집하는 정책을 유지합니다.

## 실제 처리 흐름

    `기상청 API 응답 지연`
    → `날씨 Collector 60초 timeout 및 FAILED`
    → `weather_ready_gate는 ALL_DONE으로 통과`
    → `lookback 범위 안의 마지막 SUCCEEDED 날씨 선택`
    → `이전 날씨를 STALE로 기록`
    → `필수 데이터 정상 여부 확인`
    → `수요 추론과 Gold 게시 성공`
    → `다음 5분 tick에서 날씨 수집 재시도`
