## 문제 상황
- 5분마다 따릉이 재고가 달라지므로, 수집부터 재배치 경로 생성까지 다음 실행이 시작되기 전에 마쳐야 합니다.

> **운영 결과:** AWS t4g.large에서 `realtime_tick` 53회가 모두 5분 안에 완료됐습니다. 예약 시각부터 전체 DAG 완료까지 중앙값은 135.5초이고, 95%의 실행이 151.7초 안에 끝났습니다.

## 5분 안에 끝내야 하는 범위

이 프로젝트의 최종 결과는 분석용 파일이 아니라 운영자가 확인할 **재배치 경로**입니다. 따라서 수집만 빨리 끝내는 것이 아니라 아래 전체 과정을 하나의 핵심 처리 경로로 봤습니다.

```text
재고·대여이력·실시간 인구 수집
→ 생활인구 보정
→ 12시간 수요 추론
→ 대여소·배차센터 거리 계산
→ API가 사용할 최종 데이터(Gold) 게시
→ 긴급도 계산
→ 재배치 경로 생성
```

5분 스케줄과 이전 실행의 중복을 막는 설정은 초기 Airflow DAG부터 적용했습니다. 이후 전체 경로를 실제 AWS에서 실행하며, 어느 구간이 늦는지 측정한 뒤 병목을 순서대로 줄였습니다.

## 1. 원천 API의 호출 구조에 맞춰 동시에 수집합니다

> 모든 소스에 같은 병렬도를 적용하지 않고, 실제 호출 개수와 제공처의 응답 특성에 맞춰 정했습니다.

### 따릉이 대여이력: 페이지가 많은 시간대만 4개씩 요청

따릉이 대여이력은 이용량이 많은 시간대에 한 시간 분량이 **17페이지, 16,899건**까지 늘어납니다.

| 요청 방식 | 16,899건 수집 시간 | 수집 결과 |
| :--- | ---: | :---: |
| 페이지 순차 요청 | 72.7초 | 16,899건 |
| 4개씩 병렬 요청 | 17.0초 | 16,899건 |
| 8개씩 병렬 요청 | 10.5초 | 16,899건 |

현재는 가장 빠른 8개가 아니라 **4개**를 사용합니다. 17초면 기본 수집 제한시간인 150초 안에 충분히 들어오고, 지연 도착한 대여이력을 보강하기 위한 추가 호출도 있어 공공 API에 더 많은 요청을 보내며 몇 초를 줄일 필요가 없다고 판단했습니다.

### 실시간 인구: 공식 121개 POI만 8개씩 요청

서울 실시간 인구 API는 장소별로 한 번씩, 총 121번 호출해야 합니다. 이 API의 번호 범위는 `POI001~POI131`이지만 중간에 결번 10개가 있어 숫자를 순서대로 호출할 수 없습니다.

번호 범위만 순회하면 결번에서 실패가 반복되고 정상 장소 10개가 빠집니다. 따라서 공식 POI 목록을 기준정보로 관리하고, 실제 121개 코드만 8개씩 수집합니다.

| 호출 대상 | 수집 상태 | 실제 API 실행 시간 |
| :--- | :---: | ---: |
| 번호 범위 순회 | 111/121, 부분 수집 | 47.1~48.7초 |
| 공식 코드로 확인한 121개 | 121/121, 전체 수집 | 1.755초 |

### 기상청 예보: 대여소가 사용하는 34개 격자를 8개씩 요청

대여소의 최근접 기상 격자는 34개이고, 단기예보는 격자마다 2페이지가 필요해 총 68번 호출합니다. 이를 하나씩 요청하면 50.89초가 걸렸고 당시 30초 제한 시간을 넘겼습니다.

| 요청 방식 | 단기예보 수집 시간 |
| :--- | ---: |
| 격자 순차 요청 | 50.89초 |
| 4개씩 병렬 요청 | 36.54초 |
| 8개씩 병렬 요청 | 14.45초 |

초단기실황·초단기예보·단기예보를 함께 실행했을 때도 확인한 뒤, 현재 세 소스 모두 8개 병렬 요청을 사용합니다.

## 2. 5분마다 할 필요가 없는 일은 핵심 경로에서 분리합니다

> 재고는 5분마다 바뀌지만 기준정보와 날씨는 같은 속도로 바뀌지 않습니다.

### POI 기준정보는 일별로 검증하고 5분 실행에서는 선택만 합니다

실시간 인구를 생활인구 격자에 반영하려면 서울시의 POI 목록과 영역 파일이 필요합니다. 하지만 이 파일의 다운로드, 공간정보 검증, 버전 게시는 매 5분마다 반복할 일이 아닙니다.

- 일별 파이프라인이 공식 파일의 변경 여부를 확인하고 새 버전을 검증·게시합니다.
- 5분 파이프라인은 미리 게시된 버전의 위치와 hash만 선택합니다.
- 선택한 버전은 해당 실행이 끝날 때까지 그대로 사용합니다.

이렇게 해서 공간정보 검증은 5분 경로에서 빼고, 현재 인구 보정에 필요한 기준만 빠르게 가져옵니다.

### 날씨는 발표 주기가 지났을 때만 수집합니다

기상청 데이터는 초단기실황·예보가 10분, 단기예보가 3시간 간격으로 갱신됩니다. 따라서 5분마다 세 소스를 모두 다시 호출하지 않습니다.

- 마지막 성공 수집이 발표 주기 안에 있으면 이번 수집을 건너뜁니다.
- 수집이 필요할 때만 실행하고, 재시도 없이 최대 60초까지만 기다립니다.
- 새 날씨 수집이 실패해도 이전의 유효한 날씨로 다음 단계를 진행합니다.
- 실패한 단기예보도 3시간을 기다리지 않고 다음 5분 실행에서 다시 시도합니다.

날씨 필요 여부에 따라 DAG를 네 개로 나누었던 시기도 있었지만, 실행이 늦어지면 서로 다른 DAG가 겹쳐 작은 인스턴스의 CPU를 경쟁하는 문제가 있었습니다. 현재는 **5분 단일 DAG와 소스별 갱신 주기 확인**으로 구성해 실행 중첩과 복구 지연을 함께 줄였습니다.

### 지연 도착 대여이력은 현재 경로와 나란히 보강합니다

대여이력 API는 대여 시각으로 조회하지만 반납이 끝난 기록만 보여줍니다. 늦게 반납된 기록을 회수하려고 1시간 전 데이터를 다시 수집하되, 이 작업을 현재 재배치 경로 생성의 선행 조건으로 연결하지 않았습니다.

현재는 1시간 전 한 구간만 보강해 전체 작업량을 제한합니다. 재배치 경로는 이 보강 작업을 기다리지 않고 진행하면서도, 보강 작업을 포함한 전체 DAG가 5분 안에 끝나도록 구성했습니다.

## 3. 매 실행마다 전체 데이터를 다시 처리하지 않습니다

### 생활인구는 필요한 시간대의 행만 변환합니다

생활인구 원본은 하루 약 25만 행입니다. 이전에는 현재와 향후 시각을 만들 때마다 전체 행을 Python 객체로 변환한 뒤 필요 없는 시간대를 버렸습니다.

현재는 시간대를 나타내는 `TT` 컬럼을 먼저 확인해 필요한 행의 위치를 찾고, 그 부분만 전체 컬럼으로 변환합니다. 잘못된 시간 값이 없는지는 여전히 전체 행에서 확인합니다.

| 처리 방식 | 정규화 시간 |
| :--- | ---: |
| 시각마다 약 25만 행 전체 변환 | 9.95초 |
| 시간 컬럼으로 고른 행만 변환 | 3.38초 |

### 1,639만 행의 과거 수요 패턴은 필요한 조각만 읽습니다

대여소별 과거 수요 패턴 데이터는 16,396,215행입니다. 이 데이터를 매 5분마다 전부 읽는 방식은 t4g.large의 메모리 범위를 넘기므로, 실시간 경로와 전체 검증 경로를 분리했습니다.

전체 데이터 검증은 모델을 게시할 때 한 번 수행하고, 실시간 추론에서는 현재 시각과 1시간 전 대체값에 필요한 `(월, 요일)` 조각만 읽습니다.

| 항목 | 전체 패턴 데이터 처리 | 실시간 조각 처리 |
| :--- | ---: | ---: |
| DataFrame 변환 행 | 16,396,215행 | 195,984행 |
| 선택 데이터 메모리 | 전체 데이터 | 약 4.1MB |
| 조각 로딩 결과 | t4g.large 한도 초과 | 약 1초 |

실시간 배열도 실제로 사용하는 평균값만 담아 약 250MiB에서 1.5MiB로 줄였고, 추론 프로세스의 최대 메모리 사용량도 643.5MiB에서 424.3MiB로 낮췄습니다.

## 4. S3와 RDS의 반복 왕복을 줄입니다

### S3는 최신 파일을 먼저 보고 같은 실행에서 재사용합니다

추론은 현재 시각의 생활인구와 날씨가 없으면 이전 시각의 후보를 찾아야 합니다. 모든 후보를 매번 순서대로 확인하는 대신 다음처럼 처리합니다.

- 가장 최신일 가능성이 높은 파일 하나를 먼저 확인합니다.
- 최신 파일이 없을 때만 나머지 후보를 동시에 확인합니다.
- 한 번 선택한 날씨 데이터와 S3 연결은 같은 추론 실행에서 재사용합니다.

| 지표 | 반복 탐색 방식 | 최신 우선·재사용 방식 |
| :--- | ---: | ---: |
| S3 LIST | 572회 | 80회 |
| S3 GET | 694회 | 278회 |
| 추론 시간 | 19.87초 | 10.80초 |

두 실행에서 S3로부터 읽은 전체 데이터 크기는 거의 같았습니다. 데이터를 생략한 것이 아니라, 같은 데이터를 찾기 위해 반복하던 요청을 줄인 결과입니다.

### 10만여 개 거리 관계는 PostGIS에 묶어서 보냅니다

재배치 준비 과정에서는 해당 실행이 선택한 대여소와 활성 배차센터의 거리를 계산합니다. 대여소의 신설·이전과 배차센터 상태를 반영해야 하므로 고정된 근삿값으로 대신하지 않았습니다.

AWS에서 처음 병목을 확인했을 때는 106,626개 좌표 관계를 하나씩 RDS에 보내고 있었습니다. 이 중 151초가 계산이 아니라 RDS 응답을 기다리는 시간이었습니다.

| 측정 단계 | PostGIS 호출 방식 | 거리 준비 시간 |
| :--- | :--- | ---: |
| AWS 병목 확인 | 좌표 관계별 106,626회 왕복 | 173.5초 |
| 1차 개선 | 대여소 단위로 묶어서 요청 | 34.8초 |

이후 같은 대여소 안에서도 반복되던 요청을 합쳐, 한 실행의 전체 좌표 관계를 최대 16,384개씩 나눠 보냅니다.

| 동일한 로컬 고정 입력 | PostGIS 쿼리 | 거리 준비 시간 |
| :--- | ---: | ---: |
| 대여소 단위 묶음 | 16,404회 | 8.126초 |
| 전체 관계 묶음 | 9회 | 2.343초 |

두 번째 표에서는 양쪽 모두 106,608개 거리를 계산했고, 거리 값과 최종 계획의 해시도 같았습니다. 두 표는 입력과 환경이 다르므로 하나의 연속된 전후 실험처럼 합치지 않습니다.

## 5. 제한된 인프라에서 병목을 측정해 동시성을 정합니다

운영 서버는 t4g.large 1대에서 Airflow, API, Web, MLflow를 함께 실행합니다. 무조건 동시에 많이 실행하면 메모리와 CPU가 부족하고, 너무 적게 실행하면 독립적인 수집 작업도 줄을 서게 됩니다.

실제 AWS의 한 실행은 처음에 530초가 걸렸습니다. 그중 149초는 계산 시간이 아니라 `prepare_serving_plan`이 끝난 뒤 추론 task가 시작되기까지의 대기시간이었습니다.

- 임시로 t4g.xlarge를 사용해 CPU queueing을 제거했습니다.
- 별도로 확인된 PostGIS 왕복 병목은 인스턴스 크기가 아니라 쿼리 구조를 바꿔 해결했습니다.
- PostGIS 개선까지 반영한 실행이 226초로 들어오면서 처음으로 5분 안에 전체 경로를 마쳤습니다.
- 이후 상시 인스턴스를 다시 t4g.large로 낮추고 후속 최적화를 반영한 현재 AWS 운영에서는 전체 경로가 **2분대**로 안정화됐습니다.
- 현재 Airflow 전체 병렬도와 DAG당 최대 동시 task는 모두 3이고, 같은 realtime DAG는 한 번만 실행되게 제한합니다.

각 task에는 wall time, CPU, RSS/PSS, 컨테이너 메모리와 queueing 정보를 남기는 자원 계측을 적용했습니다. 기상청 요청도 격자·페이지별 응답시간을 기록합니다. 인스턴스 크기나 병렬도를 감으로 정하지 않고 실제 대기 원인이 CPU인지, 메모리인지, 외부 API인지 구분하기 위해서입니다.

현재 수치는 릴리스 배포 후 스케줄 적체가 해소된 2026년 8월 26일 16:00~20:20 KST에 AWS t4g.large에서 연속 실행된 `realtime_tick` 53회를 Airflow 메타데이터로 집계한 결과입니다. 예약 시각부터 전체 DAG가 끝난 시각까지를 측정해 스케줄러 지연도 포함했습니다.
